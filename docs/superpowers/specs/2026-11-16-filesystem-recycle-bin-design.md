# 文件系统回收站设计

## 背景

当前删除操作仅将节点状态改为 `TRASHED`。正常文件列表会隐藏该节点，但同目录名称唯一索引和 `CreateNode` 的同名检查仍包含已删除节点。因此，用户删除文件后再次上传同名文件会收到“当前目录已存在同名文件”。

文件系统已经定义 `ACTIVE`、`TRASHED`、`PURGE_PENDING`、`PURGED` 等状态，但缺少回收站查询、恢复和彻底删除流程。本设计补齐完整生命周期，并首先修复软删除节点继续占用名称的问题。

## 目标

- 普通删除将文件或目录移入回收站，并立即释放原目录中的名称。
- 用户可以查看、恢复、彻底删除回收站项目，也可以清空回收站。
- 恢复不覆盖现有文件，不自动改名。
- 可恢复内容继续占用配额；彻底删除后释放逻辑配额。
- 物理对象仅在无任何有效引用且不受保留策略保护时由 GC 异步清理。
- 删除、恢复和彻底删除具备幂等、审计、权限和并发安全保证。

## 非目标

- 首版不自动按天数清理回收站。
- 首版不支持恢复到用户选择的新目录。
- 首版不支持恢复时覆盖或自动重命名同名项目。
- HTTP 请求不直接同步删除底层物理对象。

## 用户行为

### 移入回收站

文件列表中的“删除”统一表示“移入回收站”。确认框明确说明项目可从回收站恢复。

节点变为 `TRASHED` 后：

- 从正常列表和搜索结果中消失。
- 保留名称、原父目录、版本和存储引用。
- 不再占用原目录中的活动名称，用户可以立即上传或创建同名项目。
- 仍占用逻辑配额，因为内容可以恢复。

删除目录时只将该目录入口标记为 `TRASHED`。它的活动子树因祖先不可见而从正常文件区隐藏。回收站只显示直接处于 `TRASHED` 的入口节点，不重复展示被该目录遮蔽的活动后代。

### 回收站

文件空间顶部导航增加“回收站”入口。回收站支持：

- 分页浏览已删除项目；
- 单项或多项恢复；
- 单项或多项彻底删除；
- 清空当前空间的回收站。

彻底删除和清空回收站必须二次确认，并明确提示不可撤销。

### 恢复

恢复项目时使用原 `parent_id` 和原名称。

- 原目录存在、可写且没有同名活动节点时，恢复成功。
- 原目录不存在、已删除或不可访问时，阻止恢复，并提示先恢复父目录。
- 原目录已有同名活动节点时，阻止恢复，并提示用户先重命名或删除现有项目。
- 不覆盖现有项目，不自动生成新名称。
- 恢复目录后，其活动后代重新可见；此前被单独删除的后代保持 `TRASHED`，不会被意外恢复。

### 彻底删除

彻底删除目录时递归处理整棵子树。节点先进入 `PURGE_PENDING`，事务完成后成为 `PURGED`。彻底删除释放逻辑文件数、字节数和 Blob 引用，但物理对象由 GC 异步处理。

受保留策略或法律保留保护的项目不能彻底删除，并返回明确错误。

## 数据设计

### 活动名称唯一性

数据库中的根节点和子节点名称唯一索引改为仅约束 `state = 'ACTIVE'`：

- 根节点：`namespace_id + normalized_name`；
- 子节点：`namespace_id + parent_id + normalized_name`。

应用层 `CreateNode` 同名预检查也只查询活动节点。数据库索引仍是最终并发保护。

该规则意味着 `TRASHED`、`PURGE_PENDING`、`PURGED` 和 `RETENTION_HOLD` 节点均不占用活动文件树中的名称。

### 删除元数据

节点记录使用现有 `deleted_at` 字段记录进入回收站的时间，并新增可空的 `deleted_by` 字段记录删除操作者。回收站默认按 `deleted_at DESC, id DESC` 排序，游标包含这两个字段。列表仅返回没有 `TRASHED` 祖先的 `TRASHED` 节点，避免单独删除的子项在其父目录也被删除后重复展示。

原 `parent_id` 保持不变，用于恢复和路径展示。

### 配额与 Blob 引用

- 移入回收站：不修改已用字节数、文件数或 Blob 引用。
- 恢复：不修改配额或 Blob 引用。
- 彻底删除：按目录树中的文件和全部版本汇总逻辑用量，原子扣减配额并递减相应 Blob 引用。
- Blob 引用归零后进入现有 tombstone/GC 流程。
- GC 在删除副本前继续检查活动引用、文件链接、保留策略和法律保留。

目录递归状态更新、配额扣减、Blob 引用变更、命令去重、领域事件和审计记录属于同一数据库事务。

## 接口设计

### 查询

`GET /files/trash`

参数：

- `namespace_id`
- `limit`
- `cursor`

返回回收站入口节点、原路径、删除时间和可执行操作。

### 恢复

`POST /files/:nodeId/restore`

请求包含 `command_id` 和 `namespace_id`。恢复要求调用者对原父目录具有写权限。

### 彻底删除

`DELETE /files/:nodeId/permanent`

请求包含 `command_id` 和 `namespace_id`。彻底删除要求删除权限，并检查保留策略。

### 清空回收站

`DELETE /files/trash`

请求包含一个批次 `command_id`。服务为每个回收站入口派生稳定的子命令 ID，逐项鉴权和处理，并返回每项成功或失败结果。成功项不因其他项失败而被伪装为失败；重放同一批次不会重复扣减配额、Blob 引用或发布事件。

所有修改接口复用现有命令去重、审计和可靠事件发布模式。

## 状态迁移与并发

允许的核心迁移：

- `ACTIVE -> TRASHED`
- `TRASHED -> ACTIVE`
- `TRASHED -> PURGE_PENDING -> PURGED`

状态迁移使用带当前状态条件的更新。恢复和彻底删除并发时最多一个操作成功。

恢复与同名上传并发时，活动名称唯一索引保证最多一个成功。失败方收到稳定的同名冲突，不暴露数据库驱动错误。

根目录不能删除、恢复或彻底删除。

## 错误处理

- 恢复同名冲突：`原目录已有同名项目，请先重命名或删除现有项目`。
- 原目录不可恢复：`原目录不存在或已在回收站，请先恢复父目录`。
- 保留策略阻止删除：说明项目受保留策略保护。
- 批量操作：成功项立即从界面移除，失败项保留并显示逐项原因。
- 数据库冲突、事务重试耗尽和状态冲突使用现有稳定错误映射，不返回内部 SQL 或对象键。

## 前端设计

- 普通文件列表删除确认框使用“移入回收站”文案。
- 顶部文件空间导航增加“回收站”。
- 回收站页面复用文件浏览器的列表、网格、选择和批量操作能力，但只展示恢复、彻底删除和清空操作。
- 页面区分加载、空、无权限和错误状态。
- 恢复与彻底删除成功后刷新正常文件树和回收站计数。
- 批量部分失败时保留失败选择，并显示逐项原因。

## 测试与验收

### 持久层

- 软删除后允许创建同目录同名活动节点。
- 恢复后重新占用名称。
- 同名活动节点存在时恢复失败。
- 部分唯一索引迁移在 PostgreSQL 和 SQLite 测试模式下行为一致。
- 删除目录隐藏子树，恢复父目录不恢复单独删除的后代。

### 命令层

- 删除、恢复和彻底删除幂等。
- 根目录保护和权限拒绝正确审计。
- 彻底删除正确更新目录树状态、配额和 Blob 引用。
- 保留策略阻止彻底删除。
- 恢复与上传并发、恢复与彻底删除并发最多一个成功。

### 接口与前端

- HTTP、BFF 和 SDK 覆盖列表、恢复、彻底删除、清空和错误映射。
- 前端覆盖删除文案、回收站空/加载/错误状态、多选、二次确认和部分失败。

### 关键验收路径

1. 上传 `a.txt`。
2. 将 `a.txt` 移入回收站。
3. 在原目录再次上传 `a.txt`，上传成功。
4. 恢复旧 `a.txt`，因同名活动文件被明确阻止。
5. 彻底删除旧 `a.txt`。
6. 确认逻辑配额与 Blob 引用正确；物理对象仅在最后一个引用满足 GC 条件后删除。
